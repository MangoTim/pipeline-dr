The failover drill

Five moves. Production is never at risk until move 4 — the standby has to prove it can carry the load first.
WHAT HAPPENS — AND THE COMMAND THAT DOES IT
PROD · 192.168.147.105
DR · 192.168.147.104
1
Warm the standby
Bring the DR MCP up while PROD keeps serving. ansible/dr-warmup.yml
ansible-playbook -i inventory.ini dr-warmup.yml -> systemctl --user start rhel-mcp.service (on .104)
● live
:8095 answering
○ stopped
2
The readiness gate
Ask the standby what it can see of itself, through the MCP, before anything is cut over. scripts/mcp_dr_probe.py
podman run -i --rm --network host <image> - \ --url http://192.168.147.104:8095/mcp \ --target 192.168.147.104 \ --expect localhost.localdomain ... < scripts/mcp_dr_probe.py get_system_information / get_cpu_information / get_memory_information / get_disk_usage
● still serving
the gate runs WHILE production is up
● started
4 cores · 72 % RAM free · 77 % disk free
→ READY  |  not ready → abort, PROD untouched
3
The cutover
Stop the MCP on PROD, start it on DR. ansible/failover.yml
ansible-playbook -i inventory.ini failover.yml -> systemctl --user stop rhel-mcp.service (on .105) -> systemctl --user start rhel-mcp.service (on .104)
● still serving
until the unit is stopped
● live
:8095 now answers on .104
4
Verify the new live site
Two facts in one session: the hostname says which site is live, the socket table says the answer is real. scripts/mcp_verify.py
podman run -i --rm --network host <image> - \ --url http://192.168.147.104:8095/mcp \ --expect localhost.localdomain \ --call get_listening_ports \ --assert get_listening_ports=8095 < scripts/mcp_verify.py
○ stopped
:8095 refused
● live
localhost.localdomain, and 8095 held by
linux-mcp-server
5
Fail back
The exact mirror: stop DR, start PROD, verify again. ansible/failback.yml
ansible-playbook -i inventory.ini failback.yml -> systemctl --user stop rhel-mcp.service (on .104) -> systemctl --user start rhel-mcp.service (on .105)
● live again
answers server-gateway.example.com
○ stopped
:8095 refused
The honest line. The service moves for real: the unit is stopped on one host and started on the other. The client's address is changed by the caller — a floating IP would need ip addr add, i.e. root on the target, and this demo never gives the deploy user root. Production DR does it with VRRP/keepalived or pacemaker + corosync instead.
